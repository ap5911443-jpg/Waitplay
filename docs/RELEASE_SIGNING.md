# Release signing and notarization (macOS)

> **Status: prepared, not active.** The workflow, scripts and tests are in place, but nothing is signed or notarized yet because the
> Apple Developer Program membership is not active. Until it is, every build is an **ad-hoc signed development build**. Public
> releases made now are labelled `*-UNSIGNED.dmg` and published as pre-releases. No certificate, password or key exists in this
> repository, and none is generated by any script.

| Step | Needs the paid membership? | State |
|---|---|---|
| Hardened Runtime, secure timestamp and entitlements in `packaging/macos/build_app.sh` | No | Done (applies as soon as an identity is given) |
| Notarization through a `notarytool` keychain profile (no password on any command line) | Uses it | Done in code, **waiting** for membership |
| `sign` job in `.github/workflows/macos.yml`, secrets only in its one import step | Uses it | Done in code, **skipped** until `APPLE_SIGNING_ENABLED=true` |
| `packaging/macos/verify_release.sh` (signature, Hardened Runtime, stapled ticket, Gatekeeper verdict) | Needs a signed DMG | Done, **untested** against a real signed build |
| Creating the Developer ID certificate and the App Store Connect API key | **Yes** | **Waiting** |
| Adding the GitHub secrets, the protected environment and the repository variable | After the two above | **Waiting** |
| First signed and notarized release | **Yes** | **Waiting** |

## What stays working without Apple

`bash packaging/macos/build_app.sh <target>` with no `APPLE_*` variables builds an ad-hoc signed `VibePlay.app` and DMG. CI does
this on every push. Gatekeeper asks the user to confirm the first launch (right-click, Open).

## GitHub secrets and settings to create (names only; never commit values)

Create an **environment** named `release-signing` (Settings, Environments): add *Required reviewers* (you) and restrict
*Deployment branches and tags* to `v*`. Put these **environment secrets** in it (not repository secrets):

| Secret | What it is | How to get it (after the membership is active) |
|---|---|---|
| `APPLE_CERTIFICATE_P12` | base64 of the *Developer ID Application* certificate with its private key | Xcode, Settings, Accounts, Manage Certificates, add *Developer ID Application*. Keychain Access: export the certificate as `.p12` with a password. Then `base64 -i cert.p12 \| pbcopy` |
| `APPLE_CERTIFICATE_PASSWORD` | the password you chose for that `.p12` | you |
| `APPLE_NOTARY_API_KEY_P8` | base64 of the App Store Connect API key file `AuthKey_XXXXXXXXXX.p8` | App Store Connect, Users and Access, Integrations, Team Keys, create a key (role *Developer*). It can be downloaded only once. `base64 -i AuthKey_XXXXXXXXXX.p8 \| pbcopy` |
| `APPLE_NOTARY_KEY_ID` | the key id of that API key | same page |
| `APPLE_NOTARY_ISSUER_ID` | the issuer id of the team | same page |

The signing identity (`Developer ID Application: Name (TEAMID)`) is **not** a secret and is not configured: the import script reads
it from the certificate and fails unless there is exactly one.

Finally set the repository **variable** `APPLE_SIGNING_ENABLED` to `true` (Settings, Secrets and variables, Actions, Variables).
This is the switch that turns the `sign` job on; leave it unset until everything above exists.

## How the pipeline protects the secrets (SA-04, SA-14)

- No signing secret is at workflow or job level. They are passed to **one step** ("Import certificate and store notary
  credentials") of the separate `sign` job, which runs no `cargo` and no third-party build scripts, in a protected environment that
  needs your approval.
- The certificate lands in a temporary keychain, the API key in a `0600` file that is deleted right after
  `notarytool store-credentials` copies it into that keychain as the profile `waitplay-notary`. Later steps only know the path of
  the keychain and the profile name. The keychain is deleted in an `always()` step.
- `build_app.sh` calls `notarytool submit --keychain-profile`. There is no `--password`, `--apple-id` or app-specific password
  anywhere; `crates/waitplay-bridge/tests/repo_hygiene.rs` fails if one appears.
- The `release` job (the only one with write access) publishes the signed DMGs with SHA-256 sums and a build-provenance
  attestation: `gh attestation verify VibePlay-<version>-arm64.dmg --repo ap5911443-jpg/waitplay-website`.

## Signing on your own Mac (optional)

```sh
# once: stores your credentials in the login keychain; notarytool asks for them, nothing goes on the command line
xcrun notarytool store-credentials "waitplay-notary"
# build, sign, notarize, staple, verify
cargo build --release --workspace --target aarch64-apple-darwin
APPLE_SIGNING_IDENTITY="Developer ID Application: Your Name (TEAMID)" APPLE_NOTARY_PROFILE=waitplay-notary \
  bash packaging/macos/build_app.sh aarch64-apple-darwin
bash packaging/macos/verify_release.sh dist/aarch64-apple-darwin/VibePlay-*.dmg
```

Use `WAITPLAY_NOTARIZE=0` to sign without notarizing while testing.

## Checklist for the first signed release (all waiting for the membership)

1. Pay the membership; wait for it to become active.
2. Create the certificate and the API key; add the five secrets to the `release-signing` environment.
3. Run the workflow manually (*Run workflow*) with `APPLE_SIGNING_ENABLED=true`; the `sign` job must go green, including
   *Verify as a user's Mac will*.
4. Download the DMG on a clean Mac and open it: no Gatekeeper warning.
5. Tag `vX.Y.Z`; the release job publishes the signed DMGs (not a pre-release).
